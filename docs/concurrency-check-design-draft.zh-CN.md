# 批量双并发检测：设计草案与能力核查

日期：2026-09-21。本文保留最初讨论和能力核查记录；后续按用户批准收敛为 Kimi、MiniMax、GLM 第一阶段，现已完成本地 0.48.0 候选实现，见 `concurrency-check-implementation.md` 和 `concurrency-check-acceptance.zh-CN.md`。未进行真实供应商双并发实测，不代表全部供应商已适配。本文不含密钥或账号标识，候选版本保留此前启动修复。

## 一、已确认需求

用户在统一入口点击“检测并发”，检测设置中已勾选供应商下的全部启用 API Key。不同 Key 依次检测，单个 Key 最多同时发起两条请求。确认本次可用并发小于 2 且原因是并发限制时，对应卡片显示“并发受限”；确认双并发通过时不显示正常标签，并清除旧限制提示。网络、额度、鉴权、权限、模型配置、普通速率限制、排队与协议异常不得假装是并发限制。

全部供应商必须出现在能力核查和检测结果中。纳入任务枚举不等于已经实现实际探测；缺失适配、缺少模型调用权限或证据不足均不得计为通过。要达到“所有供应商都可实际测试”的完成条件，必须逐项关闭后文未确认项。

## 二、现有代码与本机事实

### （一）目录事实

`rust/src/settings/api_keys.rs::get_api_key_providers` 包含 39 项，`get_app_managed_api_key_providers` 排除 Alibaba 和 Grok，当前实际可添加凭据的目录为 37 项。该目录中混有模型调用 Key、管理 Key、账号登录凭据、云平台复合凭据，不可用一个聊天请求模板全部处理。

现有 `commands/credentials.rs::get_api_key_providers` 使用上述过滤目录。`rust/src/providers/codex/mod.rs` 读取 Codex 登录凭据查询用量，Codex 不在上述 API Key 添加目录。`zenmux/mod.rs` 使用管理 API；`bedrock/mod.rs` 使用 Cost Explorer/CloudWatch 查询账单和活动，不能推断现有权限包含推理权限。

### （二）验证边界

额度查询成功不能证明模型调用可用，也不能证明账号真实并发上限。能力核查与离线模拟测试不等于已对所有套餐、地区和模型组合完成线上验证。本设计记录不包含用户配置或账号清单。当前实现说明以 `concurrency-check-implementation.md` 为准。

## 四、推荐架构与运行约束

### （一）任务枚举与调度

后端读取勾选供应商与启用 Key 的稳定 ID，生成 run_id 和检查列表；前端只接收元数据，不接收密钥。每个任务在实际启动前再次检查供应商与 Key 是否仍启用、是否被替换或删除。一次全局运行覆盖所有窗口，防止重复启动。配置改变后的旧结果不能回写到新 Key。

不同 Key 串行执行，每个最多两条在途推理请求；不静默重试、不自动切模型、不升并发。取消或退出停止队列并取消在途请求。客户端断开不保证远端已释放并发或停止计费，下一项启动须考虑适配器的清理/冷却条件，未知时明确记录。用户其他设备产生的请求不受本程序控制。

### （二）供应商适配器

每个适配器说明凭据类型、目标 origin、协议、模型/部署配置、收费维度、准入规则、流式事件解析、并发证据规则和终止行为。自定义地址只向明确配置的同源目标发送凭据，禁用跨源自动跳转，不猜测转发到其他平台。不得伪装成官方客户端绕过准入。

模型应由用户指定或使用经核实的提供方固定模型；不能把可列举到模型解释成有调用权限。管理凭据不自动转换或寻找其他账户凭据。语音与 Agent 类适配必须有独立设计和明确成本边界，不能自动创建持久任务。

### （三）判断证据

两条 HTTP 连接同时打开、同时拿到 200 或先后成功，均不足以证明实际双并发。即便本地流时间重叠，也可能受服务端/网关缓冲影响，不能声称证明内部同时推理。结果详情应表述为“本次观察到双请求响应重叠”，不能声称最大并发上限已测出。

优先采用有明确定义且适用于目标模型的官方并发字段/错误。流式探测作为可用性证据需至少包含有效输出事件，不能把心跳、角色消息或连接建立计为开始生成。单路完整结束后另一条才开始输出时，结果为不确定而非受限。普通 429、403、5xx 和超时不能直接判定并发限制。

对于明确并发错误，区分“配置上限小于 2”与“本次可用并发不足 2”；外部占用可能使后者成立而前者不成立。多路额度属于同一账号时，不按 Key 数量假设并发池独立。

### （四）界面及状态

统一“检测并发”入口，预览范围、所选模型、潜在费用、无法检测项，确认后执行；展示进度与取消。每项结果为通过、并发受限、不确定、检测失败、缺少配置、待适配或已取消之一，汇总数字必须覆盖全部枚举项，跳过项不计通过。

仅“并发受限”在 Key 卡片常驻提示。通过可清除旧提示；失败、不确定、取消均不自动清除旧证据。旧证据显示最近确认时间及历史属性，不能永远冒充当前实时状态。更换 Key、模型或 endpoint 后旧证据失效。额度刷新不得改写并发结果。展示层不输出原始响应体、密钥、完整账号信息。

结果若需重启保留，应通过现有存储框架独立保存脱敏证据（Key ID、凭据修订关联、模型与端点标识、时间、分类、检测器版本），不混入 API Key 文件。此项在正式设计中需明确保存期限与过期展示规则。

## 五、验收门槛

1. 全目录覆盖测试，新增供应商必须显式声明能力，不允许静默漏项。
2. 状态分类测试：并发拒绝、普通限流、额度不足、鉴权失败、排队、心跳、流内错误及断流。
3. 模拟服务器复现双流交错与串行排队；无法识别时必须返回不确定。
4. 同账号多 Key 串行、重复点击、多窗口、取消、超时、运行时禁用/删除/替换 Key 均有测试。
5. 错误详情脱敏、重定向凭据保护、禁止自动模型回退、输出上限与读取上限验证。
6. 每个适配器需要独立协议契约和授权后的真实验收。未经实测只标记待验证，不能对外声称全部支持。
7. 正式交付更新版本号。此前全量回归中终端读取测试未通过的问题不能被本功能覆盖或忽略。

## 六、尚待决定的范围

当前确认的是 API Key 检测。Codex 等仅登录的供应商没有可加入该队列的普通 API Key。建议在结果中明确“非 API Key 账号，未检测”；若也要求主动测试它们，需要另行批准登录账号调用的设计。管理凭据及缺少推理参数的条目建议明确提示补充配置，不误报为已通过或并发受限。

本稿尚未实现“全部供应商可靠检测”的承诺，缺失协议与权限的目录项仍是工作项；不能以展示“待适配”冒充完成。

## 七、已查官方来源

1. [Kimi 错误参考](https://www.kimi.com/code/docs/kimi-code/error-reference.html)：明确区分并发、额度、普通限流和过载。
2. [Kimi 使用规范](https://www.kimi.com/code/docs/en/kimi-code/community-guidelines.html)：客户端身份与交互使用约束，手动发起不等于自动获得所有用途许可。
3. [MiniMax 错误码](https://platform.minimax.io/docs/api-reference/errorcode)：1041 conn limit 与其他限流码分开；具体接口适用性还需验证。
4. [Z.AI 错误码](https://docs.z.ai/api-reference/api-code)：1302 为请求限流；多种额度/权限错误也使用 429，流内错误需另行处理。
5. [DeepSeek 并发说明](https://api-docs.deepseek.com/quick_start/rate_limit/)：按账号和模型定义并发，不能推广到所有模型或其他供应商。
6. [ZenMux 快速开始](https://zenmux.ai/docs/guide/quickstart)：管理 API 与调用 API 分离。
7. [ElevenLabs 429](https://elevenlabs.io/docs/help-center/technical/api-error-code-429)、[模型及并发](https://elevenlabs.io/docs/overview/models)：并发错误、繁忙错误及响应头。
8. [Deepgram 限流](https://developers.deepgram.com/reference/api-rate-limits)：管理端点与推理端点分别限制。
9. [Bedrock 推理权限](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-prereq.html)：流式模型调用要求单独权限。
10. [LiteLLM 虚拟 Key](https://docs.litellm.ai/docs/proxy/virtual_keys)：存在 max_parallel_requests 配置，但不是对所有部署读取权限的保证。
11. [OpenRouter 限流](https://openrouter.ai/docs/api/reference/limits)：需区分额度与请求限流，不能作为跨模型并发结论。
